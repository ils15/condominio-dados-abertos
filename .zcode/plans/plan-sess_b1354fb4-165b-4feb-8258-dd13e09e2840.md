# Fase 2 — Conformidade, visibilidade e transparência financeira (evolução do portal)

## Contexto
O prompt traz uma especificação mais completa do sistema de dados abertos. Comparando com o que já está no ar (ils15.github.io/condominio-dados-abertos): **já atendemos** repositório por categoria, cronograma NBR 5674 com status/estimativa, histórico, prestadores e catálogo de dados abertos. **Faltam:** metadados ricos de documento (validade, ART/RRT, relatório fotográfico), **visibilidade público vs. administrativo**, **contratos** e **orçamentos** com visão de despesas. Decisão do usuário: permanecer estático (é um exemplo) — visibilidade via **build duplo**: site público (gh-pages) exclui o administrativo; a síndica gera **cópia local completa** num comando. PocketBase fica documentado como Fase 3. Entregáveis 1-4 do prompt viram o documento `docs/ARQUITETURA.md` + implementação real no sistema.

## 1. Modelo de dados (CSVs novos/estendidos)
- **`dados/documentos.csv` (novo — manifesto com metadados; substitui o scan automático):** id, titulo, categoria, arquivo, tipo (laudo, ordem_servico, nota_fiscal, contrato, certificado, relatorio_fotografico, art), data_emissao, validade (opcional), prestador_id, art_rrt, manutencao_id, **visibilidade (publico|administrativo)**, observacoes. Validação cruzada: arquivo existe em documentos/ (PDF **e imagens jpg/png**); PDF não catalogado → aviso.
- **`dados/contratos.csv` (novo):** id, prestador_id, objeto, categoria, inicio, fim, valor_mensal, status (ativo|encerrado), documento, observacoes.
- **`dados/orcamentos.csv` (novo):** id, data, descricao, ativo_id, cronograma_id, prestador_id, valor, status (aguardando|aprovado|rejeitado), documento, observacoes.
- `manutencoes.csv` ganha coluna `orcamento_id` (rastreabilidade orçamento→execução→gasto).

## 2. Gerador (`scripts/gerar_dados.py`)
- Lê/valida os 3 CSVs novos (mesmos padrões: erros em PT-BR, datas/valores/referências cruzadas).
- Calcula: documentos **vencidos/vencendo** (validade < hoje / ≤ 90 dias), contratos vigentes com gasto 12m do prestador, orçamentos por status, despesas por contrato.
- **Flag `--perfil publico|completo`**: no público, filtra tudo com visibilidade=administrativo de data.js/downloads; completo mantém tudo (e o site exibe badge "administrativo"). `npm run gerar:local` gera `dist-local/` completo.
- SQLite e datapackage.json ganham as tabelas/fields novos.

## 3. Interface (React)
- **Documentos** refeita com metadados: badge de tipo, emissão/validade (badge vermelho p/ vencido, âmbar p/ vencendo), prestador, chip ART/RRT, filtro por tipo/validade/categoria.
- **Nova página Financeiro** (sidebar, ícone ReceiptText): contratos com despesas vinculadas (gasto 12m por prestador + mensalidade), orçamentos por status com vínculo a cronograma/ativo, resumo por prestador.
- **Painel**: banner de alerta se houver documentos/contratos vencidos; KPIs existentes mantidos.
- Perfil completo: badge "administrativo" nos itens restritos (o público simplesmente não os recebe).

## 4. Documento de arquitetura (`docs/ARQUITETURA.md`) — entregáveis 1-4 do prompt
1. **Benchmarking**: CKAN (pesado, portal-padrão), Directus (admin polido, mais recurso), PocketBase (binário único+SQLite+auth+S3 — evolução natural), Supabase (completo mas self-host pesado — fontes: pocketbasecloud.com, lowendtalk.com, gist BaaS), CMMS (Atlas/openMAINT) e a opção sob medida escolhida.
2. **Arquitetura recomendada**: estático híbrido agora (grátis/zero-ops, build duplo); diagrama local→GitHub→gh-pages + caminho futuro VPS/Docker/S3.
3. **Modelo de dados**: as 7 entidades com campos e relacionamentos (o mesmo que roda de verdade).
4. **Fases**: F1 MVP estático ✓ · F2 esta (conformidade/visibilidade/financeiro) · F3 PocketBase com login e upload (script de migração CSV→SQLite pronto no gerador) · F4 domínio próprio + backups.
